# qz / bz benchmark refresh — 2026-06-24

**Hardware:** 2× Intel Xeon Gold 6254 @ 3.10 GHz (18 cores/socket, 36 cores / 72
threads, 2 NUMA nodes), 376 GB RAM, NVMe scratch.
**Threads:** `-t 72`. **Run:** single detached pass, box idle (user-confirmed
quiet window); wall/RSS are single-run, not averaged — treat ±5% as noise.
**Tools:** qz/bz 0.3.0, SPRING (order-preserving, no `-r`), samtools 1.23, pigz 2.8.
**Wall:** ~58 min end-to-end (18:15 → 19:13). All roundtrips passed
(20 `OK` / 3 `PASS` / 3 `QUAL_ONLY_DIFF` / 2 `n-a`; zero `MISMATCH`/`FAIL`).

`raw_bytes` is the per-row ratio denominator: R1 for single-end rows, R1+R2 for
paired rows, the (reheadered) input BAM bytes for bz/CRAM. Codec-comparison rows
run `--numa off` so size/ratio reflect the codec, not multi-socket sharding; the
one `qz_default_numa_auto` row is the deliberate on-vs-off speed pair.

`comp CPU%` / `decomp CPU%` are `/usr/bin/time -v`'s "Percent of CPU this job got"
(**7200% = all 72 threads saturated**); they expose parallel efficiency and the
memory-bandwidth ceiling — e.g. `qz_default` compress at 2047% (~20 cores, one
socket, BWT bandwidth-bound) vs `qz_default --numa auto` at 3381% (~34 cores, both
sockets), the source of its 33.5→23.5 s speedup. All values are single-run.

**pigz baselines (added 2026-06-25):** the single-end 30M tier already carried a `pigz -9`
row (5.03×) from the main pass; matching `pigz -9 -p 72 -c` baselines were since added for
the paired (5.12×), reference single/paired (5.23× / 5.12×), and BAM (1.00× — a re-gzip of
the already-BGZF/DEFLATE BAM neither shrinks nor verifies anything new) tiers, via
`benchmarks/bench_pigz_all.sh`. Reference/paired share the same raw reads as the
paired/reference-paired rows, so pigz is a pure generic-gzip floor there; all four round-trip
`OK`. Box load crept up to ~18 during the BAM run's tail (pigz is the only consumer; the
sub-3 s BAM compress is unaffected).

  (+0.103×); `use_tok` adds 0.000× and `use_arith` +0.004×. And `use_fqz` is *fqzcomp*
  — the identical htscodecs codec bz already uses for quality — so CRAM's strong mode
  only reaches parity with bz on quality. bz wins overall via its non-quality streams
  (consensus-delta sequence + columnar fields), and the name tokeniser being a no-op
  here re-confirms the earlier "read-name tokeniser is a dud on sorted BAMs" finding.
  **Correction (2026-06-25):** the earlier pass reported CRAM at 1.25–1.29×, which was
  a harness bug, not a CRAM property. The BAM was aligned to `GRCh38_full_plus_hs38d1`
  (2580 `@SQ`, incl. decoys) and carries no M5 tags, but the harness fed CRAM the
  decoy-less `no_alt` reference; samtools could not resolve every `@SQ`, silently
  enabled `embed_ref=2` (it embeds the reference INTO the CRAM), and the file bloated
  to ~2.0 GB. With a contig-matching reference (`Homo_sapiens_assembly38.fasta`,
  verified 2580/2580) CRAM is 1.77×/1.83×/1.94×. `bench_cram` now aborts any row that
  falls back to `embed_ref`. The BAM is genuinely coordinate-sorted (0 out-of-order
  POS over 18.3M records); sort order was never the cause. CRAM still **decodes ~3×
  faster** (9–11 s vs bz's ~28 s) and uses far less compress RAM — bz's edge is ratio
  plus needing no reference at all (exactly the case the no-M5 BAM exposes).
- **Levels are a memory/speed dial, ratio ~flat** (2.00–2.01×), confirming the level
  preset is not a ratio lever.
- **Lossy quality** (`--reduce-quality`) is the real ratio lever: 2.00× → 5.10/6.37/
  6.93× at L1/2/3, with everything-but-QUAL byte-identical (`QUAL_ONLY_DIFF`).

## qz vs SPRING — head-to-head

SPRING is FASTQ-only (no BAM). The fair axis is **whether read order is retained**:
SPRING with no flag already reorders internally for compression and stores a
permutation to restore order, so even "order-preserving" SPRING reaches reorder-tier
ratios; qz default does **not** reorder. qz's order-retaining answer is `--reference`
(map to the genome). `qz --cluster` and `SPRING -r` both drop order. Rows added this
pass (script `bench_spring_compare.sh`): `qz_default_paired` (order-preserving) and
`SPRING -r` for single 30M / single chr20 / paired chr20 (multiset-verified `PASS`,
since `-r` permutes). `c s`/`d s` = compress/decompress wall; `d RSS` = decode peak.

**Sharding speedup (off → auto):**

| mode | compress | decompress |
|---|---|---|
| single 30M | 1.49× | 1.47× |
| paired chr20 | 1.16× | **1.75×** |
| reference single | 1.67× | **1.80×** |

BAM would shard cleanly. `--numa auto` (the shipped default) is a free decode win on
multi-socket hardware and a zero-overhead in-process fallback on a single socket.
`--cluster` was excluded from this sweep (near-serial decode, minimal NUMA benefit).

**Takeaways:**
- **GPU's compress win is concentrated in ultra (big blocks):** 30M ultra-2 **195 → 114 s
  (1.71×)**, 5M ultra-2 35.6 → 21.5 (1.66×). At the **default 25 MB block with `-t 72`,
  GPU compress is ~a wash** (30M 34.8 → 34.2) — the CPU already parallelizes the many
  small BWTs across 72 cores while the single GPU serializes them through one lock. So
  the GPU is an **ultra-mode lever**, not a default-mode one at high `-t`.
- **NUMA is the bigger decode lever** (and wins default compress: 30M 34.8 → 22.9, 1.52×);
  for **ultra compress NUMA does nothing** (one big block at a time → nothing to shard).
- **GPU × NUMA: complementary, not conflicting, but sub-additive.** Both workers share
  the one GPU without VRAM-OOM or corruption (all byte-identical, all `OK`). They **stack
  best on decode**: 30M ultra-2 **16.5 s (1.96×)**, 5M ultra-2 4.55 s (1.92×) — better than
  either alone. On compress the single GPU caps stacking: 30M default GPU+NUMA 19.1 s
  (1.82×, mostly NUMA + a little GPU), but 30M ultra-2 GPU+NUMA ≈ GPU alone (NUMA has
  nothing to shard). **They target overlapping bottlenecks** (the BWT scatter), so you
  don't multiply the two speedups.
- **Bonus:** GPU **lowers** compress RSS in ultra (BWT workspace moves to VRAM): 30M
  ultra-2 4.5 → 3.4 GB.
- **Best single config per axis:** ultra compress → **GPU** (or GPU+NUMA, same); default
  compress → **GPU+NUMA**; decode (any) → **GPU+NUMA** (ultra) / **NUMA** (default).

**Takeaways:**
- **bz: GPU is a *regression*** — compress 26.3 → **59.4 s (2.3× slower)**, CPU% collapsing
  2035% → 715%. bz's BSC work is many small per-stream blocks that parallelize across 72
  cores on CPU; the single GPU serializes them through one lock. **NUMA is bz's lever**
  (decode 36.9 → 28.2 s, 1.31×). Don't build bz with cuda.
- **cluster: GPU irrelevant** — compress flat (124 → 117 s, noise). `--cluster`'s sequence
  is **zstd-long** and quality **fqz** (neither is BSC); only a tiny `StrandBits` stream is
  BSC, so the GPU has almost nothing to accelerate. NUMA is flat too (one big zstd block +
  fqz, little to shard). The small decode dip (62.7 → 53.7 s) is the StrandBits BSC inverse.
- **reference: GPU is a dud** — reference compress is **serialization-bound** (the in-order
  coverage fold), so the GPU BWT win on the big consensus/fallback BSC streams is masked:
  ref-single 26.7 → 22.5 (modest), ref-paired 43.0 → 48.3 (slower); **GPU+NUMA can even
  regress** single compress (26.2 s — GPU contention across the two NUMA workers negates
  NUMA). **NUMA is the reference lever** (decode 1.7–1.8×). Confirms the prior "reference =
  GPU dud" analysis empirically.
- **Net across all modes:** the *only* place GPU clearly wins is **qz ultra** (big serial
  BSC blocks). Elsewhere it's neutral (cluster), serialization-masked (reference), or
  harmful (bz). **NUMA is the broadly useful lever; GPU is a targeted ultra-compress
  accelerator.**

> GPU is opt-in and needs a GPU + the CUDA runtime present (the cuda binary dynamic-links
> `libcudart`); the shipped default build is CPU-only and portable.

## Roundtrip oracles (per mode)

- **md5 of reconstructed FASTQ** → `OK`/`MISMATCH`: qz default/fast/ultra/reference,
  SPRING, pigz.
- **`qz verify`** → `PASS`/`FAIL`: `--cluster` (output is a permutation; multiset
  checksum, not md5).
- **sorted-record multiset md5** → `PASS`/`FAIL`: `SPRING -r` (also permutes; SPRING
  has no verify, so input vs decoded records are sorted + md5-compared, pairs kept
  together for paired-end).
- **`samtools view | md5sum` fingerprint**: bz lossless = full record stream
  (`OK`); bz lossy = QUAL-stripped (`$11="*"`) fingerprint → `QUAL_ONLY_DIFF`.
- **`n-a`**: CRAM (ratio/speed competitor; roundtrip not re-verified).
